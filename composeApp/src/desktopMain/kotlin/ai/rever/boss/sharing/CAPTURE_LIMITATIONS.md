# Exact application capture

The macOS 14+ adapter captures the selected Compose window and up to seven visible owned Compose windows/dialogs. Each source is bound to a live NSWindow number and the current process ID, then captured with its own desktop-independent ScreenCaptureKit filter. The host composites only these verified sources. It never captures a display, chooses by title, or selects the first available window. Background and occluded window capture is supported. Geometry, ownership, native handle, modality, and surface membership are fenced before input; resize/dialog changes discard old frames and advance geometry revision.

Capture starts and expansions are available through the native macOS Window menu and the title-bar Sharing menu. Title-bar capture entries are explicitly local-only: remote toolbar dispatch disables them in its menu and rechecks that restriction when selecting an entry. There is no capture-start keyboard shortcut or remotely clickable content action. Settings can select windows but cannot activate capture. Any future start entry point must preserve this local-consent boundary.

Owned overlays use an actual native owner on all desktop platforms, including nested overlays. Each surface is resized using its logical dimensions in the shared coordinate space so mixed display density cannot double a popup size. Multiwindow composition uses premultiplied BGRA source-over on an opaque black backdrop. Exact synthetic macOS capture verifies clear and half-opacity pixels and their composition over the captured owner. Linux BSC2 helper frames preserve premultiplied alpha, verified through the actual header/payload under Xvfb, Weston 1x/2x, and KWin. Opaque BSC1 helpers remain supported. Windows still exports opaque alpha; its transparent overlay fidelity remains unverified and is not implied by the host blend tests.

Owned surfaces currently follow AWT ownership enumeration order. Overlapping sibling popups whose native stacking order changes are not yet verified: composition and hit testing can use stale sibling order. Exact native stacking snapshots remain required before claiming complete popup fidelity.

Unknown owned native windows fail closed. Native menus, arbitrary system sheets, IME, and non-Compose native popups still require native identity and input adapters; they are not silently substituted with display pixels. All content inside selected application windows is visible to admitted viewers, including sensitive tabs. There is no automatic secret redaction.

One continuous ScreenCaptureKit `SCStream` per verified source serves one publication, regardless of viewer count. The stream supports 60 FPS with a bounded native queue and keeps only the latest complete BGRA pixel buffer. Publication starts at 30 FPS, promotes to 60 after ten healthy encoder samples, and returns to 30 after two CPU-pressure or excessive-encode-time samples. Bandwidth pressure alone leaves frame rate unchanged while WebRTC adapts resolution. Idle/reset counters cannot trigger a promotion. The authenticated loopback request carries the selected rate back to native capture; ScreenCaptureKit applies that rate without restarting the stream or dropping the final changed frame before an idle period. Contiguous native buffers use one bulk copy instead of one native call per row. Older publishers without the optional rate header keep 30 FPS. Native filters and window enumeration are created when the source/layout changes, rather than for every frame. Pixels pass through a host-only capability-protected binary loopback endpoint into a BGRA VideoFrame and MediaStreamTrackGenerator, then the existing encrypted VP8 WebRTC publication. The direct path avoids the canvas upload/capture step and allows only one awaited frame write; newer source frames remain latest-only in the native mailbox. Engines lacking compatible direct-frame APIs use a canvas: a WebGL fragment shader converts BGRA channels on the GPU, reusing texture storage until dimensions change, with a CPU conversion fallback when suitable WebGL is unavailable. Idle keepalive repeats the retained frame or texture; clearing demand/authority replaces it with black and retires the old pixels immediately. The production path performs no PNG encoding, Base64 conversion, or compressed-image decode. The direct path still copies pixels through loopback and converts their color format internally; this is not a zero-copy hardware-encoder pipeline.

The source has a maximum long edge of 1920 without upscaling. The publisher configures native-scale encoding and its 8 Mbps ceiling before negotiation. A bounded 4 Mbps VP8 startup estimate avoids the conservative initial bandwidth ramp; this is not a minimum, and congestion control may reduce it. Explicit lower codec caps/start estimates remain respected, and engines rejecting the optional hint retry the original encrypted answer. A synthetic encrypted browser check delivered its first frame at 1920×1080 and held that size for five seconds on loopback; this does not establish WAN/SFU startup quality. Owned dialogs use separate exact native streams and uniform raw-pixel composition. WebRTC prefers frame rate and can adapt resolution under CPU or uplink pressure; a default 8 Mbps ceiling gives desktop text bitrate headroom without forcing that bitrate or overriding an existing cap. Receiver-specific downstream adaptation remains limited by the single published encoding. No native stream runs without viewer demand; static/idle publication uses a blank or repeated canvas keepalive. Late pixels are discarded if geometry, demand or publication changed. Session deactivation, display sleep, and system sleep stop the publication through documented JDK Desktop listeners; missing platform event support disables capture. Stopped shares never resume automatically after unlock. Actual OS lock delivery still needs hardware validation; tests inject the same stop event without locking the user's machine.

Control-capable browser and native viewers request control on connect by default, honoring account admission and the single-controller lease. View-only roles do not request control; a busy controller is never displaced. Failed or canceled acquisitions release any late server grant before their bridge closes. The viewer releases control on blur, hidden-page transitions and disconnect.

The native macOS title bar remains installed during sharing. Synthetic production-shaped inactive windows verify actual close/minimize/zoom button pixels with glass enabled and disabled; a follow-up encrypted VP8 browser check also retained those pixels at native size. Inactive macOS controls are dimmed by AppKit, and severe video downscaling can reduce them to only a few pixels. Controller-owned toolbar item tags and exact native view/window ownership map remote clicks to app callbacks; native address editing uses only the selected NSTextView, with bounded AppKit dispatch and current browser/toolbar identity checks. Remote toolbar menus and address suggestions use captured owned non-focusable Compose dialogs. Remote events never invoke NSApplication menus or full-app capture start/expansion.

Input goes only to descendants of snapshot windows. Swing browser views and visible Compose browser surfaces use scoped JxBrowser dispatch with engine focus. Compose surfaces are selected by their exact host window and measured content-pane bounds, including display density; neither the active tab nor the first browser is a fallback. Removing or relocating a composition retires its keyboard authority. A one-shot exact browser/window/key permit lets the production browser callback accept authenticated remote dispatch while the owner is inactive; ordinary background keys remain suppressed, and remote dispatch bypasses host shortcut routing. AWT keys explicitly bypass global focus retargeting. No Robot or OS-wide key/pointer injection is used. Parent controls cannot bypass a captured modal child. Production supports scoped background input without bringing the host window to the foreground. Synthetic non-focusable Compose and Swing windows verify text entry and button activation without OS focus; input cannot reach an unrelated active application. Opt-in isolated Chromium tests verify trusted webpage typing, selection, and deletion without OS focus; split-pane routing and switching back to host address fields have synthetic window coverage. Accelerated content still requires the real-application fidelity check. The host installs a backend-verified controller lease, and Kotlin independently checks peer, session, generation, window, geometry revision, expiry, and sequence. Releases occur on revoke, expiry, geometry replacement, window removal, and target unavailability.

Opt-in native tests create only synthetic test windows. They check selected-window pixels under an unrelated occluder, Retina dimensions, owned-dialog composition, stale geometry, actual background Compose/Swing text/button delivery without OS focus, session-loss teardown, and demand gating. These tests do not certify mixed accelerated browser/terminal/editor fidelity, IME, or every native menu/system dialog. Tests use display color-management tolerance rather than claiming byte-exact RGB values.

The loopback raw-frame bridge negotiates `X-Boss-App-Wait: true`. A reader can wait up to 250 ms for a new mailbox sequence; the response explicitly acknowledges this mode before the client removes its extra polling delay. Old clients and servers retain polling. Each host page admits one pending request, with a shared pool of 16 workers and no queued frame work, separate from control/asset requests. A two-second total deadline interrupts stalled writers and closes their exchange. Negotiated requests require an empty body, exact origin and host capability, and a valid sequence. Page retirement clears pixels, wakes waiters, and cancels negotiated delivery; late capture callbacks cannot resurrect retired pixels. Admission retries are bounded, and the client awaits each frame upload before requesting another.

## Other desktop platforms

Windows and Linux X11 have packaged native-helper adapters behind real OS/session capability probes. Helpers are built from this repository during native packaging, launched only from the application resource directory, and bound to the launching JVM's PID plus exact native window handle. Binary BGRA frames use a bounded versioned pipe with strictly increasing sequence and fixed geometry; the JVM keeps only the latest frame. A separate helper monitors session authority even when capture is paused by minimization or missing viewer demand. Native compilation and synthetic Xvfb tests are evidence for those specific boundaries, not certification of interactive Windows/Linux support. The remaining platform validation requirements are explicit below:

- Windows 10 2004/build 19041+: the implemented native WinRT/D3D11 helper binds `IGraphicsCaptureItemInterop::CreateForWindow(HWND)` to the exact Compose HWND and live parent PID, verifies `GetWindowThreadProcessId`, and consumes a bounded free-threaded frame pool. Cursor suppression is mandatory and sets this minimum version. GPU scaling precedes bounded SDR BGRA readback; this is not zero-copy hardware encoding. Window closure or geometry changes retire the stream. Initial WTS session-state and secure-desktop checks, lock/disconnect notifications, suspend/resume, and display-off events fence session authority; a separate watchdog terminates blocked output. Hosted Windows x64/ARM64 CI compiled and packaged the helper and fixture with warnings as errors; invalid-parent and unknown-mode CLI tests passed. Manual hosted runtime tests passed exact normal-root capture on both Windows Server 2025 x64 and Windows 11 ARM64. The required nonfocusable owned utility popup passed on ARM64 but Server x64 rejected every tested owned-popup style at CreateForWindow, both in the source process and helper process. This unresolved eligibility gap is not evidence about Windows 11 x64. The runners use Microsoft Basic Render Driver; actual BossConsole capture/input, physical GPU performance, DPI, modal, session, sleep, and signing validation remain required. `PrintWindow`, desktop BitBlt, and title lookup are prohibited. See `native/app-capture/WINDOWS.md` for exact build/test commands and remaining runtime evidence.
- X11: the helper verifies the Compose client XID through XRes and captures its topmost non-root WM frame via `XCompositeNameWindowPixmap`. The selected client is authorized content; other frame branches must belong to the window manager, excluding sibling application windows. The WM itself is verified through root/self EWMH `_NET_SUPPORTING_WM_CHECK` and XRes PID identity; unmanaged application ancestors are rejected. XDamage gates changed frames and XRender scales on the server before requested-resolution pixel readback. The pixmap's explicit output color format is used because `XGetImage` on a pixmap has no source visual. The Xlib error handler exists only in the isolated helper. Logind checks require an active, unlocked X11 or Wayland session with an available X display, and lock/sleep signals are terminal. Physical AWT insets are checked against the exact native client and a bounded crop inside its verified WM frame; incompatible dimensions/aspect ratios are refused rather than stretched. Synthetic Xvfb tests cover selected pixels under an occluder, wrong PID rejection, resize invalidation, idle capture, final changed frames and spatial downscaling. Real JDK17 AWT pixel/local-coordinate fixtures also pass under decorated Weston at compositor scale 1 and 2 (JDK reports scale 1) and KWin/Breeze at scale 1. Forced Java UI scale 2 with scale-1 WM chrome is explicitly unsupported until a richer native/client coordinate mapping exists. Accelerated browser surfaces, actual BossConsole input, mixed DPI, logind lock/switch/suspend, and display power still require desktop validation.
- XWayland uses that same exact-XID adapter for current JDK/Compose windows, with no portal or source-name selection. Native Wayland surfaces remain unsupported: the standard ScreenCast portal returns a selected PipeWire stream and source type, not proof that it is the caller's supplied Compose window. Its parent-window identifier only positions the consent dialog. An exact source-identity mechanism or a separately authorized picker flow is required; source names and first-stream heuristics are not acceptable.
