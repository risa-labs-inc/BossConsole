# BOSS v9.5.16

**Release Date:** 2026-09-14

A reviewed batch off `dev` (#649) covering 68 files. The theme is consent that was promised and
never asked for: the browser's executable-download warning was an empty TODO block, two kernel IPC
bridges accepted any local caller, and a plugin could read any other plugin's stored data by naming
its id. Alongside that, MCP approval can now trust a whole plugin at once, and an external command
prompt is a queue rather than a single slot that later requests overwrote.

## Highlights

- **The executable-download warning now actually appears.** `warnForExecutables` defaulted to true
  and its KDoc promised a confirmation before a recognized executable finished downloading, but the
  branch meant to show it was an empty TODO ("for now, just proceed") - so every user on every build
  downloaded executables silently, with no way to turn off a warning that did not exist. The
  confirmation follows `pickSaveFile`'s own pattern, since both answer the same synchronous
  `StartDownloadCallback` and both need a blocking answer: a Swing dialog through
  `invokeAndWait` that fails closed and treats an unshowable dialog as a cancel, releasing the
  claimed save path. It resolves a real owner window (active window, then any other registered
  window, then refuse) and brings it forward, so the modal cannot appear behind BOSS with the
  JxBrowser callback thread waiting on it. `Settings > Browser > Downloads` carries the toggle,
  indexed for Settings search, read live at download time so a change applies to the next download
  without a restart (#484)
- **A plugin can no longer read another plugin's stored data by asking for it.**
  `TrackingPluginContext` - the only `PluginContext` a plugin's own code ever holds - passed the raw
  `PluginStorageFactory` straight through. That factory takes an arbitrary plugin id per call and
  the desktop implementation persists purely off that string
  (`~/.boss/plugin-data/{pluginId}/storage.properties`), with nothing checking that it names the
  caller, so `context.pluginStorageFactory?.createStorage("victim-plugin-id")` was enough to read,
  overwrite or `clear()` it. `ScopedPluginStorageFactory` binds `createStorage` to the context's own
  construction-time id and ignores whatever the caller passes, the same shape
  `DownloadCenterProviderImpl.forPlugin` already uses (#548)
- **Two more kernel IPC bridges require a verified caller.** `SupabaseServiceBridge` is a generic
  Postgrest proxy over the signed-in user's own RLS-scoped session: its `rpc()` reaches the same
  `create_secret` / `update_secret` calls `SecretServiceBridge` exists to protect, and `select()`
  reads any table RLS exposes. `DownloadServiceBridge.openFile` / `revealInFolder` shelled out to
  the OS default-handler command for any path that exists on disk, which is an arbitrary-file
  execution primitive that bypasses the executable-download consent above entirely. Both now
  require a verified process identity on every RPC with audit logging, and open/reveal are confined
  to a path this provider's own downloads list is tracking, compared canonically so a symlink or a
  `..` cannot walk out (#550)
- **MCP approval can trust a whole plugin at once.** A plugin with several mutating tools meant
  approving each one individually in the same session. "Trust This Plugin" persists a provider-wide
  ALLOW covering every tool that provider contributes, including ones added by later versions.
  DENY at either level still wins first and unconditionally, an explicit per-tool ASK still
  overrides provider ALLOW, and the button sits in its own row below the main actions so a fast
  click cannot land on the broadest grant this dialog can make. "Trusted plugins" in the bottom bar
  lists and revokes them (#542)

## Features

- **Provider-wide MCP trust**: `McpToolPolicyConfig` gains a `providerRules` map keyed by provider
  id, and `policyFor(toolName, providerId)` resolves both levels - DENY anywhere first, then session
  trust, then an explicit tool rule, then the provider's ALLOW, then the risk-based default.
  `setToolPolicy`, `setProviderPolicy` and `revokeProviderPolicy` share one persist-and-report
  helper so a change to how a write failure is surfaced cannot update one path and miss the others,
  and revocation removes the key rather than rewriting it to a neutral value. The provider write
  takes the same `preserveDeny` / `expectedRevocation` guards under the same lock, so a reset landing
  while the dialog is open refuses the write instead of persisting a grant that reset was meant to
  invalidate. A genuine disk fault records `PROVIDER_TRUST_PERSIST_FAILED` and falls back to session
  trust for the one approved tool rather than withholding a call the operator already approved (#542)
- **A toggle for the executable-download warning**: `Settings > Browser > Downloads > "Warn before
  downloading executable files"`, on by default, persisted through the existing
  `BrowserSettingsManager` JSON store. `BrowserSettings.warnForExecutables` is `@Volatile` - written
  on the Compose UI thread, read on the JxBrowser download callback thread - and the unpersisted
  `DownloadSettings` copy is gone, so there is one live flag. Disabling it skips only the warning;
  filename checks, save-path handling and cancellation cleanup are unchanged (#484)

## Bug Fixes

- **Co-browse control payloads are validated before they are spliced into page JavaScript.** Remote
  control objects are checked recursively and unquoted expressions rejected, while valid control
  messages and escaped string data are preserved (#549)
- **A plugin's file panel has an owner and its own directory mode.** `FilePickerProviderFactory`
  created every panel as `FileDialog(null as Frame?, ...)` and showed it with a bare
  `isVisible = true`, which is two different failures. With no owner the panel has no window to be
  modal to and none to come forward over, so it can open behind the Compose window and the
  `onResult(null)` that follows reaches the plugin looking exactly like a cancel. With no directory
  mode, `apple.awt.fileDialogForDirectories` is process-wide and read by the native peer at
  creation, so a panel opened inside the browser's folder panel came up as a directory chooser.
  `NativeFileDialogs` had already solved both for the browser's own panels, so this extracts that
  helper and deletes its private duplicates rather than adding a third copy; `withDirectoryMode`
  clears an absent property rather than writing back "false", restores a present one verbatim,
  unwinds nesting in reverse and restores after a throwing body (#551, #552)
- **One pick now produces one answer, and a dotted extension filters.** `onResult` was called inside
  the same `try` that catches picker failures, so a plugin whose callback threw received its path
  and then a `null` immediately after - indistinguishable from a cancel. Delivery goes through
  `deliverOnce`, which sets its flag before invoking. Separately, the API takes `List<String>` and
  says nothing about spelling, so plugins pass both `csv` and `.csv` while every consumer appended
  its own dot: the macOS filter tested `".$ext"` and Swing's `FileNameExtensionFilter` adds the dot
  itself, so `.csv` was matched as `..csv` and the filter hid every valid choice instead of narrowing
  to them. `normalizedExtensions` strips a leading dot and drops blanks on both platforms, in Open
  and Save (#552)
- **An explicit Ctrl chord fires on the Control key off macOS.** Capture and matching rules are
  shared, and chord identity is platform-aware for conflict detection and migration, with distinct
  macOS modifiers preserved and unsupported Super capture rejected (#553, #559)
- **A minimized window is restored before it is focused.** Iconified frames are de-iconified through
  either `WindowFocusManager` entry point, preserving maximized state (#560, #561)
- **The CLI readiness queues no longer lose commands.** Four `ConcurrentLinkedQueue` plus
  `@Volatile` flag pairs each had the same race: a command checked the flag, found the handler not
  ready and enqueued it just after the readiness transition had drained the queue, so it was
  enqueued to nobody. `ReadinessQueue` transfers a value atomically either to the caller once ready
  or to the readiness transition that claims the deferred batch, with claimed values executed after
  the monitor is released. Deferred logging is guarded too (#633)
- **An external command approval prompt is a queue, not a single slot.** A second
  `boss://terminal?command=` arriving while the first was still awaiting confirmation overwrote it,
  so a request the operator was never shown was silently dropped. `TerminalCommandApprovalQueue` is
  a window-owned FIFO, bounded at 16 pending so a flood cannot grow it without limit, and `consume`
  matches by identity so only the request actually on screen can be consumed - once - even when two
  commands are textually identical. The dialog shows the pending count and re-arms its 500ms
  confirm delay per distinct request, so a double click cannot carry through to the next one.
  Holding a command is logged only after the enqueue succeeds (#649)

## Improvements

- **The two client-grant shapes that produced the same class of bug three times are now gated.**
  `ALTER DEFAULT PRIVILEGES` hands every later table client grants, and three tables then shipped
  with a permissive write policy on top: `plugin_downloads` (#488), `completed_authentications`
  (#536) and `secret_access_log` / `plugin_api_key_logs` (#538). Each was caught by a person reading
  a migration, and the existing identity-disclosure audit could not reach any of them - it asks who
  can READ identity, its checks filter `cmd in ('SELECT','ALL')` so an INSERT policy is invisible,
  and it filters on RLS being off while both #538 tables had RLS enabled with a permissive policy.
  `supabase/audit/client_grant_audit.sql` adds two exact catalog checks: G1 names any public table a
  client role can reach without RLS, and G2 names any INSERT/UPDATE/DELETE/ALL policy reachable by
  `anon`, `authenticated` or PUBLIC whose predicate is the literal `true`. G2 keys on the predicate
  rather than on a missing `TO` clause, because the missing `TO` is how all three slipped past review
  but 101 of this schema's 128 policies omit it - predicate plus write plus client role matches two
  policies in the whole schema, and both are the ones #538 removed. Restrictive policies are excluded
  from the write lint (#596)
- **Convention tests scan the checked-in source tree, not `build/`.** The `.kt` walk now skips
  `build` directories: including them made a convention test's result depend on which Gradle tasks
  happened to run first, and let generated copies of a file create false positives (#508)

## Known Limitations

- **Provider-wide trust is broader than it looks, by design.** It covers tools a later version of
  the plugin adds, and a replacement plugin claiming the same provider id. Sibling prompts already
  queued when trust is granted still ask. The Trusted plugins UI lists ALLOW rules only, so a
  hand-edited provider DENY still needs policy-file editing to remove
- **The queued MCP approval gap from 9.5.15 is narrowed, not closed.** The provider-wide write now
  rechecks revocation and DENY under the policy lock, so a reset landing while the dialog is open
  refuses it - but calls already authorized to execute are still not cancelled
- **The file panel's owner selection is untested.** `withDirectoryMode` has seven tests and
  delivery/normalization eleven, but the owner resolution and the panel itself cannot be exercised
  from a headless test. The Save path's filter narrows what is listed and does not constrain what
  the user types, so a returned save path may still carry any extension or none
- **Thirteen kernel IPC service bridges remain unauthenticated.** #550 closed the Supabase proxy and
  Download bridges on top of the secrets and RBAC bridges from #505. The rest still trust every
  caller
- **`SandboxedPluginContext` still passes the storage factory through unscoped.** That is deliberate,
  matching the existing `downloadCenterProvider` precedent: `TrackingPluginContext` wraps it and is
  the only context a plugin ever sees, so a second scoping layer would be redundant rather than
  defensive
- **No Compose-level tests for the two new MCP dialogs.** There is no test harness for this UI layer
  on this branch; the policy precedence, persistence and revocation are covered at the engine level
