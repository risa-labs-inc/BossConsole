# BOSS v9.5.14

**Release Date:** 2026-09-11

A build-only release. One line changed outside the release notes and the version file: the
`boss-plugin-api` pin moves from 1.0.88 to 1.0.89 so the host compiles and serves the native model
catalog surface (#494). No host source, no resource and no other dependency moved, so nothing in
the application behaves differently on its own - what changes is the API level installed plugins
resolve against.

## Highlights

- **The host now serves api 1.0.89.** `gradle/libs.versions.toml` is the single source of truth for
  which API level the host implements, and `plugin-platform/plugin-api-core` downloads exactly that
  release's jar from the `boss-plugin-api` GitHub releases and filters `ai.rever.boss.plugin.api`
  out of it locally - there is no Maven registry and no fallback in that path. So this one number
  decides what a plugin calling the model catalog surface finds at runtime: against 1.0.88 those
  members are simply absent, whatever the plugin was compiled against (#494)
- **It also raises the `minApiVersion` ceiling.** `DynamicPluginLoader` hard-fails a plugin whose
  declared `minApiVersion` exceeds the api layer the host serves, with `PluginApiLevelException`,
  and that is a refusal to load rather than a degraded feature. A plugin declaring
  `minApiVersion: 1.0.89` could not load on any host before this release and can on this one (#494)

## Dependencies

- **boss-plugin-api** 1.0.88 to 1.0.89, for the native model catalog API (#494). The bump is
  consume-only from the host's side, the same shape as the 1.0.88 terminal-tab bump in v9.5.9:
  nothing in `composeApp` or `plugin-platform` was changed to implement it, and the pin exists so
  the members resolve against the api the host actually loads. The forced ordering the pin comment
  records still applies - the api release has to exist first, because `fetchApiPluginJar` 404s CI
  otherwise

## Known Limitations

- **What 1.0.89 adds is not written down in this repository.** Every pin since 1.0.79 carries a
  paragraph in `gradle/libs.versions.toml` naming the members it adds and the api PR it
  corresponds to, and that comment block says of itself that it is the only such record - it was
  not extended here, so it still describes 1.0.88 while the pin below it reads 1.0.89. The commit
  subject is the whole in-repo account of this release. Worth restoring at the next bump, for the
  reason the comment already gives: `fetchApiPluginJar` has no Maven fallback, so a pin that
  dropped a type surfaces as an unrelated compile error rather than as a missing dependency
- **A superset was not verified here.** The earlier pins each state explicitly that the new release
  is a superset of the one it replaces and that nothing a host module or an installed plugin
  resolves has been withdrawn. Nothing in this range asserts that for 1.0.89; the release builds,
  which establishes it for the host's own call sites and not for an installed plugin's
- **No user-visible change ships in this release.** A build that pins a newer contract is not a
  feature until a plugin uses it, and the plugin side of the model catalog surface is released
  separately from this repository
