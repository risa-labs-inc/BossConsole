# BOSS v9.5.10

**Release Date:** 2026-09-09

A validation batch (#414) promoting eleven reviewed changes off `dev`, plus the screen-capture
permission fix (#307). One new feature - a speaker glyph on tabs that are playing audio - and the
rest corrective: closing a browser tab no longer closes the native browser out from under a
renderer call that is still running, two plugins loading the same class name concurrently could
define it twice, a panel's Decompose lifecycle was never destroyed, paste-without-formatting could
permanently downgrade a rich clipboard to plain text, and a JNA `LinkageError` could leave a
screen-capture request unanswered forever. No dependency moved.

## Highlights

- **A tab that is playing audio says so.** Chromium reports `AudioStartedPlaying` /
  `AudioStoppedPlaying` directly, so the glyph appears and disappears the moment playback changes -
  on background tabs and inactive panels too, with no polling. It crossfades inside the existing
  favicon slot, so the title's available width never changes and the strip does not reflow under
  the pointer (#314, closing #308)
- **Native browser close now waits for admitted renderer calls to drain.** A timed-out or
  cancelled coroutine does not terminate a blocking JxBrowser round trip, so the old
  timeout-then-`browser.close()` shape could close the native object underneath a call that was
  still inside it. `DrainingBrowserExecutor` signals actual executor termination - including
  synchronous failures, RPC failures and cancelled queued jobs - and the wait suspends in a
  host-owned scope, so the tab or plugin that requested disposal cannot cancel it (#412,
  consolidating #312 and #409)
- **Two concurrent first loads of one class name can no longer define it twice.**
  `PluginClassLoader` overrode `loadClass` with the `findLoadedClass` lookup and the definition
  outside any lock, so two threads could both miss and both define. The body now runs under
  `getClassLoadingLock(name)`, and the loader registers as parallel-capable so independent names
  still make progress concurrently instead of serializing on the loader (#324)
- **Paste without formatting stops destroying a rich clipboard on a second press.** The restore
  was guarded by text equality, which by construction cannot tell "our plain write is still
  current" from "an earlier press already restored the rich original" - their string projections
  are the same text - so two presses inside the 200ms window downgraded the clipboard permanently.
  `PasteWithoutFormattingSession` tracks a JVM-local marker per write, and a user copy made during
  the window still wins (#316, closing #205)

## Features

- **tabs**: `TabAudioRegistry` is UI-thread state keyed by stable tab identity, so plugin-defined
  tab models get the indicator too. It retains a token rather than a browser or a panel callback,
  and queued deliveries read the latest level, so a close or a pause cannot be undone by stale
  work. `TabAudioSource` subscribes before it seeds, so an event arriving during the native
  `isPlaying()` read wins; publication is by browser ownership, so the state lands on the tab that
  owns the browser. The whole `browser.audio()` subscription is wrapped, because it is
  engine-backed and runs during browser setup, where a shape mismatch must degrade to "no
  indicator" rather than to a dead browser. The glyph shows in the tab strip and in the
  Top of Mind dialog (#314, closing #308)

## Bug Fixes

- **browser**: `BrowserHandleImpl.dispose()` invalidates the handle and detaches its UI
  synchronously - before a window can destroy its AWT peer - and `BrowserNativeDisposal` closes
  the browser only once all four owned executors terminate. The ten-second mark is diagnostic
  only: it warns once with the handle id and then keeps waiting, and never authorizes the close
  (#412)
- **browser**: profile release follows native close through `disposeBrowserResources`, so a
  cancelled service waiter cannot strand an already-unregistered browser or leave its profile
  fence locked, and a failed native close retains a potentially still-live profile rather than
  deleting it. Both `BrowserService` entry points return without awaiting native close (#412)
- **browser**: `executeJavaScript` stays on `BoundedBrowserCall` rather than moving to JxBrowser's
  async `Consumer` overload, which does not invoke its consumer on RPC error - so that callback
  alone cannot settle a native-operation count. This is why the drain signal is executor
  termination and not success accounting (#412)
- **browser**: named-profile creation and seeding acquire the fence through
  `acquireManagedProfileLock`, which waits at most ten seconds and then reports that the profile is
  still in use, instead of suspending indefinitely. A timeout or cancellation during handoff gives
  the lock back (#412)
- **browser**: a clipboard access failure retires the pending restore rather than letting a later
  paste resurrect stale content, and the deferred restore is armed *before* the synthetic Cmd+V is
  dispatched, since that dispatch can throw when the browser closes. Leaving plain text in place is
  the safe side of every failure here - pasting formatted text later is recoverable, destroying a
  fresh copy is not (#316, tests retained from #408)
- **panels**: `PanelComponentStore` gives each cached panel its own `DefaultComponentContext` with
  an independent `LifecycleRegistry`, instead of sharing the window's - so isolated StateKeeper
  keys, a lifecycle-bound InstanceKeeper and a standalone BackDispatcher per panel. The lifecycle
  starts at `CREATED`, which makes a factory that registers cleanup and then throws destroyable
  even though it never reached `resume()` (#317, closing #313)
- **panels**: `destroyLifecycle` continues from the advanced state after a failing `onPause` or
  `onStop` callback, because Essenty advances state before dispatching and an exception otherwise
  interrupts `destroy()` before `onDestroy` ever runs. A failure in `onDestroy` itself is terminal
  and is not redelivered (#317)
- **panels**: window teardown disposes panels in the **same** disposal callback as
  `plugin.dispose()`, and before it. Compose forgets sibling effects in reverse order, so relying
  on the separate store effect meant the plugin's classloaders could close first (#317)
- **plugins**: `markUnloading`'s contract is corrected in place. New child-first misses stop
  delegating to the parent, but own-jar and shared-class loads still work during teardown, and a
  parent lookup admitted while `ACTIVE` can finish after the marker - the per-name locks are a
  definition guard, not an unload barrier (#324)
- **capture**: `Native.load` throws `UnsatisfiedLinkError`, which is an `Error` and not an
  `Exception`, so the old `catch (e: Exception)` around the `CoreGraphics.INSTANCE` initializer did
  not catch it - a JNA binding failure escaped `StartCaptureSessionCallback` as an
  `ExceptionInInitializerError` and left the capture request with neither a grant nor a cancel.
  `ScreenCapturePermissions` contains binding *and* symbol invocation through `runCatching`, and
  both now **fail closed**: the request is cancelled rather than proceeding into a capture that
  cannot work. The binding is lazy and its failure is cached, so a broken load is attempted once
  rather than per call (#307)
- **ipc**: `ContextMenuProviderProxy` sent `actionId = label`, so two items sharing a label
  collided. Ids are now `advisoryActionId(label, index)` - unique within one ordered menu (#30)
- **logging**: all ten of `SecretService`'s catch blocks were silent. When the organisation
  migration broke every secret RPC (#144), the only WARN in the log came from the *calling plugin*,
  which is why an outage that emptied every secret panel read as a cosmetic glitch. Each catch now
  logs `LogCategory.NETWORK` with the operation and the exception *type* only - never the message
  or the throwable - because `sanitizeSupabaseFailure` rewrites serialization failures and nothing
  else, and other exceptions can carry server-echoed secret values (#145)
- **logging**: `sanitizeExceptionMessage` redacted a hostname only inside a URL. A bare hostname -
  exactly what `UnknownHostException.getMessage()` produces, so every DNS failure, and what a
  proxy-connect failure looks like - matched none of the path, URL or email patterns and passed
  through untouched. For a user behind a corporate proxy the failing hostname *is* the sensitive
  part: it names an employer and an internal topology (#109)
- **crash**: `SubmitResult.Error` held a raw exception string, sanitized at exactly one render call
  site. The constructor is private with `@ConsistentCopyVisibility`, and a companion `invoke` is
  the only way to build one - so the guarantee is a property of the type rather than something each
  future consumer (a copy button, a toast, a log line) has to remember. `CrashReportServiceTest`
  pins both entry points as private in compiled bytecode (#311, closing #110; original
  construction tests from #404)

## Improvements

- **logging**: the hostname pattern is deliberately narrow rather than "any 2-6 letter word".
  Labels must be lowercase-hostname-shaped and the trailing label must be one of a short explicit
  list of real TLDs or `internal` / `local`. `internal` and `io` are also real lowercase package
  segments (`kotlinx.coroutines.internal.ScopeCoroutine`, `kotlinx.io.EOFException`), and what
  separates those from a host is what follows: a TLD ends the token, a package segment is followed
  by `.NextSegment`. The trailing `(?!\.[A-Za-z])` is that check, added after the first version of
  the pattern redacted a live Kotlin package name out of the existing realistic-stack-trace test
  (#109)
- **browser**: `BoundedBrowserCall` and the three per-handle executors in `BrowserHandleImpl` share
  one `DrainingBrowserExecutor` definition instead of four hand-rolled single-thread pools, so
  ownership of the drain signal lives in one place. Thread behaviour is unchanged: daemon, created
  on first call, retired after 30s idle (#412)
- **browser**: `reconcileOrphanedBrowsers` and window teardown go through the same synchronous view
  teardown and the same deferred native path, so there is one release path rather than two that
  could disagree about whether a fence was dropped (#412)
- **browser**: the plugin-facing KDoc on `BrowserHandle.dispose`, `BrowserService.disposeBrowser`,
  `createBrowser`, `seedProfile` and `deleteProfile` now states what returning does and does not
  guarantee - that native release can outlive the call, that `deleteProfile` immediately after
  `disposeBrowser` may refuse, and that `seedProfile` throws after its ten-second wait (#412)
- **cleanup**: the commented-out `BossTopRunBar` and Lanager context-menu blocks are deleted (#91,
  #93), with their two `ForbiddenComment` detekt baseline entries, and `docs/SUBSYSTEMS.md` no
  longer lists Global Search as disabled - it ships as the double-shift search (#414)
- **ci**: `build.yml` builds and PR-gates `dev` as well as `main`, so a validation batch is tested
  before it is promoted. `claude-code-review.yml` moves from `pull_request` to `workflow_run`,
  because a fork `pull_request` run never receives secrets even after workflow approval - it now
  follows the approved build using trusted default-branch workflow code, never checks out a fork
  or consumes its artifacts, resolves the PR through the API (fork `workflow_run` payloads can omit
  `pull_requests`), re-checks the head SHA after fetching the mutable diff, and treats all diff
  text as untrusted data. `.github/scripts/test-claude-review.cjs` runs in `build.yml`, and
  `claude.yml` pins the CLI version (#413)
- **tests**: fourteen new files. `BrowserNativeDisposalTest`, `BrowserDisposalWiringTest`,
  `BrowserHandleExecuteJavaScriptTest` and `ManagedProfileFenceTest` cover the disposal boundary
  including a caller timeout that must not permit closing a still-running native call;
  `PasteWithoutFormattingSessionTest` and `ClipboardRestoreAfterPasteTest` inject clipboard
  suppliers and never touch the user's system clipboard, with the double-press regression pinned;
  `PluginClassLoaderConcurrencyTest` and `PluginClassLoaderConcurrencyLifecycleTest` check parallel
  registration, shared-name and superclass loads, and independent-name progress;
  `TabAudioRegistryTest`, `TabAudioIconTest` and `PanelWindowTeardownTest` cover delivery,
  last-writer-wins, ownership-checked unregister and window teardown ordering;
  `ScreenCapturePermissionsTest` pins fail-closed behaviour, one-attempt caching, and that a
  non-mac platform never loads the native binding at all (#414, #307)

## Known Limitations

- **A wedged renderer retains its browser and profile until its calls return.** That is the
  deliberate choice over closing native state underneath them after an arbitrary timeout. This is
  not an abort primitive and not an engine-recovery policy, and it does not coordinate external
  raw-JxBrowser callers or engine-level forced closure (#412)
- **There is no guaranteed shutdown flush.** The cleanup scopes use daemon threads and the shutdown
  hook does not drain them before forced engine close and process exit, so a pending native close
  or profile cleanup can be abandoned at exit. Ephemeral leftovers are reclaimed on the next
  managed-profile creation (#412)
- **The 200ms paste window is a heuristic, not a Chromium acknowledgment.** AWT offers no atomic
  compare-and-set against other processes, so a native copy landing between the final ownership
  read and the restore can still win or lose (#316)
- **Hostname redaction is selected, not complete.** Multi-level public suffixes such as `.co.uk`
  are rejected by the package-name guard, matching is case-sensitive, and unlisted suffixes and IP
  literals pass through unchanged (#109)
- **Screen capture now fails closed on a mac where CoreGraphics cannot bind.** Capture is refused
  rather than attempted; the previous "assume granted" answer skipped the rationale dialog and let
  a capture proceed that the OS would deny anyway (#307)
- **Context-menu action ids are unique within one ordered menu only**, not across edits or across
  menus, and the passive kernel bridge still discards them - they remain advisory. Stable per-item
  ids are protocol work (#30)
- **Only browser-backed tabs can report audio.** The glyph slot is generic and keyed by tab id, but
  nothing outside `BrowserHandleImpl` publishes into the registry yet (#314)
