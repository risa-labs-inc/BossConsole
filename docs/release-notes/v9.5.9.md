# BOSS v9.5.9

**Release Date:** 2026-09-08

Six changes, all corrective. A plugin id could be locked out of the store permanently once its row was unpublished; a reload on Windows could bring back the version the update had just replaced; a plugin re-enabled after its dependency was removed came back silently broken; and the scrollbar thumb was invisible on every dark panel in the app. Plus the crash dialog's own footer at the minimum window size, and the `boss-plugin-api` pin moving to 1.0.88 for the terminal-tab surface.

## Highlights

- **An unpublished plugin can be published again.** `get_plugin_with_stats` ends in `WHERE p.published = true`, which is right for the storefront and wrong for the four publish paths that used it to decide between creating and updating. An unpublished row was invisible to that lookup while still holding the unique `plugin_id` index, so publish took the create branch and the INSERT failed with 23505 - the publisher saw "Plugin ID already exists" on an HTTP 500, and no route could ever publish that plugin again. boss-plugin-rparecorder hit this on every release attempt (#345)
- **A reload on Windows no longer picks up the jar the update replaced.** `delete()` can return false while the JVM still holds a lock, so the previously-loaded jar survives the updater's cleanup and position-based ordering reloaded from it. When the running jar and the installer's recorded jar both exist and both manifests parse, the higher manifest version wins now (#291)
- **Re-enabling a plugin reports the dependency that went missing while it sat disabled.** After #178 a required dependency can be removed with its dependent disabled, and `enablePlugin` / `handleAccessChange` registered without ever asking `missingFor` - so the plugin came back apparently fine and quietly did nothing. Both paths raise the same prompt the install flows do, through `DynamicPluginManager.onPluginActivated` (#384, closing #283 and #315)
- **The scrollbar thumb is visible on dark panels, everywhere.** Compose paints it `Color.Black` at 12% alpha unhovered, which communicated neither "there is more below" nor a drag target. The style is derived at the `BossTheme` root, so every `VerticalScrollbar` / `HorizontalScrollbar` under it - host and plugin panels alike - inherits it with no per-call-site opt-in (#303, closing #106)

## Bug Fixes

- **plugin-store**: `getPluginForPublish` is a direct table read with no `published` filter, used at all four publish decision sites - the create-plugin route, the version publish route, `POST /github` and `POST /github/metadata`. `get_plugin_with_stats` is deliberately left alone, since dropping its filter would list unpublished plugins to every storefront visitor (#345)
- **plugin-store**: fixing only the lookup would have made publish return 200 while leaving the plugin invisible, so the two GitHub publish paths also set `published = true` and log when they restore a previously unpublished row. Nothing in that function ever sets `published = false` - admin delete is a hard delete - so this cannot be reversing a moderation action taken through the product (#345)
- **plugins**: `resolveReloadJarPath` compares manifest versions when both known candidates survive their existence check. Equal versions, and every case where no candidate yields a parseable version, keep the original position preference (the running jar first), which is exactly the order the resolver had before version awareness. The plugin directory is still not part of the comparison: a routine reload must not silently swap to a stray dev build or a pinned downgrade that declares a higher version under the same id, nor race a download streaming onto a scannable `<pluginId>-<version>.jar` name (#291)
- **plugins**: `PluginReloadVersion` compares all prerelease identifiers and ignores build metadata for precedence, because the shared plugin API comparator only supports a subset of prerelease formats. Numeric identifiers compare by digit count then lexically, so a long version number cannot overflow into the wrong answer (#291)
- **plugins**: an RBAC-hidden plugin keeps `enabled = true` - the hide step only sets `state = DISABLED` - so `canAccess(manifest)` is the single gate on the re-enable report rather than a second state-based one, and RBAC re-activation reports through `handleAccessChange` when access actually arrives (#384)
- **plugins**: the crash-recovery Restart path goes through `enablePlugin` too, and was raising the store-install dialog at it. `restartOwning` passes `reportMissingDependencies = false`: recovery is not activation (#384)
- **plugins**: login is a baseline, not a prompt. `PluginAccessTransitions` reports only when the access snapshot changes *for the same authenticated user*, so the first access snapshot, sign-in and account switches reconcile silently while a later grant to that user reports (#384)
- **crash**: at the crash window's 450dp minimum the three-button footer was over-subscribed - roughly 386-402dp of content width against the ~459dp the buttons wanted - and Compose's `Row` squeezes that shortfall into its *last* child rather than overflowing, shredding "Report Issue" onto two lines and "Submitting..." onto four, down to an ~88dp button. The three buttons are extracted and laid out with a `BoxWithConstraints`: side by side above `FooterActionsInlineMinWidth` (480dp), stacked full-width below it, the same width-breakpoint shape `HomeHeader` / `AuthScaffold` / `BossDialog` already use here (#304, closing #104)
- **crash**: a stacked footer leaves less room for the body, so the nested stack-trace viewport is capped at half the remaining space as well as at `TRACE_PANE_MAX_HEIGHT` - otherwise the trace pane eats the room the rest of the report needs to stay reachable (#304)
- **theme**: `CrashReportDialog` keeps its own copy of the scrollbar fix, because it renders through its own `ComposePanel().setContent` root with no `BossTheme` ancestor, so the provider never reaches it. Both copies now use the same colors (#303)

## Improvements

- **theme**: the thumb color is `textSecondary` at full alpha, not `textMuted` at 45%. The first cut measured 1.01-1.32:1 against `panel` across the six themes, below the 3:1 UI-component contrast floor in every one of them; `textSecondary` clears it in all six at 4.97:1 worst case, and is what `PanelScrollbarConfig` already uses for its own thumb. Hover steps up to `textPrimary` rather than introducing a third color the design system does not already use here (#303)
- **plugins**: manifest versions are read only when two or more candidates survive - a single survivor cannot be out-voted, so the read is skipped. `resolveReloadJarPath` stays pure, with `exists`, `relocated` and `manifestVersion` injected, and `onManifestVersionReadFailed` lets a caller log a candidate that will be scored as if it had no version, so a mis-scored reload is diagnosable (#291)
- **plugins**: advisory reporting is detached from the Enable caller. `reportPluginActivation` is queued on the manager's scope, checks jar files on `Dispatchers.IO` outside the registration lock, and uses the captured manifest - so caller cancellation cannot stop the delegate persisting a successful enable, while disposing the manager still cancels queued reports. Manifests that declare no dependencies skip it entirely (#384)
- **plugins**: a redundant enable does not re-offer, and the reporter is bound once outside the `onPluginActivated` callback rather than re-allocated on every activation (#384)
- **tests**: `DependencyPromptOnReenableTest`, `PluginAccessTransitionsTest` and the activation-policy predicates pin the re-enable behaviour as pure functions, with a sabotage run confirming that dropping the opt-out, restoring the state key, dropping the gate or un-hoisting the reporter each fails exactly the guarded tests (#384); `ReloadJarPathTest` and `PluginJarTestFixtures` cover the version comparison without a filesystem (#291); `CrashDialogFooterActionsTest` pins the 480dp breakpoint with no display, and a layout test confirms the primary button is no longer narrower than its stacked siblings at the minimum window size (#304)

## Dependencies

- **boss-plugin-api** 1.0.87 to 1.0.88 (boss-plugin-api#50, which consolidated #47/#48/#49 into one release so this pin moves once rather than three times). It adds `initialCommand` overloads on `splitVertical` / `splitHorizontal`, `renameTab`, and `tabActivity` / `tabActivityFlow` / `sendCommand` / `sendInterrupt` on `TerminalTabPluginAPI`. Nothing here is for the host to implement - the host only consumes that interface through `TerminalAPIAccess.getProvider()` and terminal-tab is the implementor, and every addition carries a default body, so no existing implementor gains an abstract member. The bump is needed so a plugin calling these resolves them against the api the host actually loads instead of finding them absent (#393)

## Known Limitations

- **The reload version comparison can redirect away from the running jar.** When both known candidates exist, a higher manifest version in the `installed.json` record wins even though the running jar is still on disk. Same directory, same user, no privilege boundary crossed - documented trade-off rather than a defect (#291)
- **The crash dialog's *submitting* state stays untested.** `isSubmitting` is private state unreachable without a network call, the same gap #104 itself calls out (#304)
- **The re-enable prompt does not chase transitive dependencies or check versions**, matching the install-time prompt it shares a bus with (#384)
