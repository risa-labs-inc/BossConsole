# BOSS v9.4.5

**Release Date:** 2026-08-09

Right-click opens a real macOS menu instead of a drawn one, which is the only kind that cannot be painted behind the browser page it belongs to, and the host finally reads the `dependencies` in a `plugin.json` at install time and offers to install what is absent. Plus an authenticated RISA Codex GLM gateway with the credential exchange kept host-side, and two repairs to paths that were failing silently: a plugin reload after an update loaded the jar the update had just deleted, and six dialogs plus every plugin toast were rendering behind the browser surface.

> **macOS 13.0 (Ventura) or later is required**, unchanged from v9.4.0 - the bundled JxBrowser 9.4.0 engine declares `LSMinimumSystemVersion 13.0`.

## Highlights

- **Right-click gives you a real macOS menu.** Under `HARDWARE` rendering, Chromium composites a native window over the Compose scene, so a drawn popup is painted behind the page it belongs to - the reason the heavyweight-window path exists at all. An OS menu is an OS-owned window, so it is immune by construction rather than worked around, and the native branch is checked before the heavyweight one because it subsumes it. The engine lives in `plugin-ui-core` behind expect/actual, so plugins - which resolve `ai.rever.boss.plugin.ui.*` parent-first from the host - get the same menus instead of the host keeping a private copy. Routing sits inside the `ContextMenu` composable, the one place both entry points already funnel through, so no call site changed. macOS only, on the same verified gate as BossTerm: Windows `TrackPopupMenu` is unverified and may block the EDT, and Linux's XAWT peer ignores GTK. Settings, Window Appearance, Menus turns it off, and the section is hidden where the toggle would do nothing (#157)
- **A plugin whose dependency is missing now says so, and offers to fix it.** `plugin.json` `dependencies` were read in exactly one place - the check that refuses to uninstall a plugin something else depends on. Nothing looked at them when a plugin was *installed*, so installing a plugin whose dependency was absent produced no signal at all and the user met the consequence later, as a feature that silently did nothing. The AI Gateway made it concrete: jupyter-notebook, llmrpa and flow-tab each declare it and each falls back to an unconfigured panel. The host now resolves the manifest against what is installed and offers to install what is missing, from all three paths that install on a user's behalf - the plugin-manager install and update flows, the first-run wizard and the update bridge - and never from startup restore, the bundled-plugin load or a reload, none of which is a user asking for anything (#156)
- **RISA Codex GLM, a provider whose credential nobody types in.** You are signed in to BOSS and an organisation gateway mints a short-lived scoped key for that identity. The exchange stays host-side and that is the point rather than an implementation detail: nothing on `PluginContext` exposes the Supabase access token, so `CredentialBrokerClient` hands a plugin the *downstream* credential and never the session that bought it. A broker is named by id, never by URL - an `exchange(url)` shape would have handed every installed plugin a way to post the user's session token to a host of its choosing (#136, #155)
- **A plugin update could take the plugin out until the next restart.** A reload is most often triggered *by* an update that already replaced the jar, and the reload took its path from the loaded plugin record - which is the file the update just deleted, since the store writes a version-named jar and removes the old one. The unload half succeeded and the load half failed. Seen live updating fluck-browser 1.2.14 to 1.2.15, with nothing retrying and the browser unloaded for the rest of the session. It fails this way for any system-plugin auto-update that changes version (#151)

## Features

- **menus**: real macOS context menus, shared in `plugin-ui-core`. `java.awt.PopupMenu` is peered onto an `NSMenu`, with four measured facts shaping the code: `show()` does not block; nothing cancels an open menu, so `hide()` is advisory and correctness rests on a generation fence; there is no dismissal event on any AWT mask, but an open menu holds the input grab, so "clear on the next input event" is sound; and `MenuShortcut` is display-only. Position comes from the cursor rather than the passed offset, which is node-relative in Compose pixels where a native menu needs screen coordinates. Added on top of the ported engine: separator hygiene, since menus assembled with `if` guards routinely produce leading, trailing or doubled separators that a native menu renders as stray lines (#157)
- **menus**: icons on native menu items, at the right size. `java.awt.MenuItem` has no icon API but its macOS peer does - `sun.lwawt.macosx.CMenuItem` declares `public setImage(Image)`, and the JDK's own comment says the intended access is an `instanceof` on the peer. Reached through the *public* `AWTAccessor` interface rather than the accessor's implementation class, since the implementation is an anonymous class in `java.awt` and going through it would need an `--add-opens` this app does not set. Sizing was a real bug and not a tuning value: `CImage.createFromImage` treats a plain bitmap's raw pixel dimensions as the point size, so rasterising at display density produced a 32pt icon on Retina and a correct one on a 1x screen. The bitmap is now a fixed 2x of a 16pt base wrapped in a `BaseMultiResolutionImage`. All best-effort - this is private JDK API, so any failure drops the icon and keeps the menu rather than taking the right-click down (#157)
- **plugins**: offer to install a missing dependency. `PluginDependencyResolution.missingFor` answers what is absent and `MissingDependencyDialog` offers to install it, using `PluginRepository.getPlugin(id)` plus `downloadPlugin` to turn an id into a jar - which is the part only the host can do, where a plugin holding a null API can only send the user to the Toolbox to search by name. Optional dependencies are reported and flagged rather than dropped, since an optional dependency is how a plugin says "this feature needs that plugin" and all three gateway consumers declare it optional. The bus is a `Channel` rather than a `SharedFlow`, because a broadcast would put the same dialog in front of every open window and let each of them start the same install. Transitive dependencies are deliberately not chased and `PluginDependency.version` is ignored - presence is by id, matching the existing uninstall check (#156)
- **llm**: an authenticated RISA Codex GLM gateway, and credential brokers served to plugins by id. `CredentialBrokers` owns the id-to-endpoint map; `CredentialBrokersTest` pins that ids are unique (a duplicate would silently shadow one), that every broker declares an https endpoint, and that each publishes a `scopedTo` prefix a careful plugin can check before posting a bearer token. `RisaLlmTokenCommand` drops from 179 lines to 40 and becomes an adapter over the same registry, so the `BOSS llm-token` helper Codex invokes and the plugin-facing path cannot drift apart or hold two copies of the endpoint. `brokeredCredentialProvider` is overridden in all three `PluginContext` wrappers including `SandboxedPluginContext` - missing that one returns null for every plugin, silently, which has happened before with `mcpToolRegistry` (#136, #155)

## Bug Fixes

- **plugins**: reload from the installed record when an update replaced the jar. `resolveReloadJarPath` checks candidates against the filesystem - the loaded path while it still exists, else the installer's recorded path, else re-resolution by plugin id from the directory. The loaded path keeps priority so an in-place hot reload is untouched and only the already-failing case changes, and a stale record cannot silently downgrade a plugin that is running fine. Relocation is the third candidate because the record alone is ordering-dependent: a reload landing between the download and the `installed.json` write sees two stale paths. Resolving *before* the unload also means a reload that cannot succeed no longer tears the running plugin down first. The same bug was still live in `DynamicPluginManager.reloadPlugin`, which is what the Reload Plugin and Reload All Plugins menu actions call - and since Reload All loops every plugin, one menu click after a background system-plugin update could force-unload several and bring none of them back (#151)
- **ui**: six dialogs were routing behind the browser surface, and it was a scope bug rather than a missing call. `LocalHeavyweightOverlays` was provided around a 20-line span while six dialogs composed later in the same window sat outside it - they already called `BossDialog`/`BossAlertDialog` so they looked converted, but the local read its `false` default. The screen-capture picker (reported for screen sharing in the fluck browser plugin), Reset Browser, Reset Terminal, the screen-recording rationale, CLI installation and import data. JxBrowser 9.3.0 has no native picker API to defer to - its capture package exposes source enumeration and session control only - so the picker UI is ours and overlay routing is the only available fix. `MemoryPressureNoticeDialog` was the last raw `Dialog(` import in host source, which an earlier PR title had claimed was already true; converted, and `NoRawDialogConventionTest` now pins it (#150)
- **ui**: plugin toasts render above the browser too, in a third overlay renderer rather than an existing one. `HeavyweightHud` is parent-sized and a non-focusable AWT window still receives mouse events with no portable click-through, so it swallows every click beneath it - fine for a Ctrl+Tab switcher held up while a key is down, not for a toast that lingers while the user keeps working; `HeavyweightPopup`'s scrim dismisses on any click, so clicking anywhere in the app would eat the click and kill the toast. `HeavyweightCorner` is content-sized, so it covers only the toast. Routing is bounded to a focused window: `ToastDuration.INDEFINITE` skips auto-dismissal entirely and the host raises one itself for a disabled plugin, which would otherwise pin an always-on-top, click-eating window over other applications with a frame-clock loop running the whole time (#150)
- **ui**: the toast overlay's size ratcheted shut, silently. `PluginToastHost` composes its padded `Column` whether or not there are toasts, so an empty host measured 32x32 from its own padding - non-zero, so it passed the zero-guard, shrank the window, and every later toast was then measured *inside* that window, measured clipped, and could never grow back. Placement stayed correct, nothing warned, every gate stayed green. Fixed in two parts because either alone is insufficient: an early return on an empty list, and `Modifier.measuredAgainst` measuring content against a constant ceiling so the answer no longer depends on the window's current size. The ceiling is then clamped to the parent, because it is a hard clip and not a soft start - three wordy toasts from arbitrary plugin content would put the bottom toast's dismiss button outside the window, on the one path where dismissing is the only way out (#150)
- **ui**: corner placement anchored to the frame, so a top-end overlay sat on the title bar. `rememberOverlayParentBounds` reads `window.locationOnScreen` and the window's own dimensions, which include the native title bar and borders; the parent-sized renderers cannot see this because they cover a superset either way, but a corner anchor can, and since the overlay eats clicks it would have covered the window controls. It converts through the content pane now. Bounds also never refreshed - `remember(parent)` keyed on an instance that never changes, so the comment claiming the parent's movement was handled was simply false; free for the sub-second overlays that came before, wrong for one the user can drag the window out from under (#150)
- **menus**: three engine correctness bugs found in review. The focused-window shortcut in invoker resolution applied none of the documented filters, so with several windows open the focused one need not contain the click and the menu landed far from the pointer. `show()` reported success before it could know a menu would appear, so a null invoker returned true to a caller that had already skipped its fallback and the right-click did nothing at all - the exact outcome the fallback exists to prevent. And `hide()` bumped the generation unconditionally while routinely running from teardown triggered *by* the menu dismissing itself, so any `ActionEvent` still queued behind it failed the fence and the item the user just clicked silently did nothing (#157)
- **menus**: the fallback was never taken, and recomposition reopened the menu. `show()` documents that false means "draw your own menu" and every guard clause exists to make that decline possible, but the composable dismissed itself and returned, so *no* menu appeared - reachable through no pointer, no showing frame, a throwing `locationOnScreen`, a failing `popup.show`, or running off the EDT, several of which are sticky rather than transient. Separately, `DisposableEffect` keyed on `items`, which is rebuilt on every recomposition and whose lambdas capture unstable values, so an open tab menu was being torn down and reopened under the cursor many times a second - the tab bar recomposes on each line of terminal output (#157)
- **menus**: an item with an empty submenu and a real `onClick` vanished on the native path. The conversion branched on `subMenu != null` while the drawn renderer uses `!isNullOrEmpty()`, so it became an unopenable dead row that the planner removed - reachable through the plugin API, which maps `subMenu?.map { }` and hands back an empty non-null list. Also: the item action had no `try`/`finally` around dismissal, and the action is `invokeAttributed` which rethrows by design, so a throwing plugin callback left the popup attached and the caller's state saying a menu was up with no further right-click able to reopen it (#157)
- **menus**: plugin actions would have run unattributed. The native conversion used `item.onClick` raw, dropping `PluginExecutionBoundary.invokeAttributed`, so the next plugin crash would have taken the app down instead of the plugin. Caught by the existing `ContextMenuAttributionTest` - exactly the silent failure its KDoc warns about - and now pinned by two more tests (#157)
- **menus**: the favorite star showed the current state rather than the action. "Unfavorite Workspace" carried a filled star and "Favorite Workspace" an empty one, so the icon described the state the workspace is already in while the label beside it described the opposite. Flipped at both sites, since it is the same item in the tab right-click menu and the empty tab-bar menu (#157)
- **llm**: key issuance was unbounded per user, and refresh raced the app's own. `/auth/token` minted a fresh 8h key on every call with only per-key rpm/tpm limits, so N calls gave one account N x 60 RPM and N rows in LiteLLM's database, while Cloud Armor's ceiling is keyed on IP rather than user; a live key is now reused until its refresh window elapses and the limits are applied to the LiteLLM user, with a request failing rather than issuing an unbounded key when that cannot be written. And `RisaLlmTokenCommand` called `refreshCurrentSession()` directly from the IPC handler thread while the client runs with `alwaysAutoRefresh` - Supabase rotates the refresh token, so an overlapping refresh presents an already-used one and the recovery policy maps that to `ClearSession`, dropping the user to the login screen mid-session. Both callers go through the single-flight `CoreAuthService.refreshSession()` now (#136)
- **llm**: upstream error text reached the client and the body-size limit was bypassable. The proxy forwarded up to 1600 characters of the LiteLLM/vLLM error body, which routinely carries the model config and `api_base`; clients get a message this gateway owns, keyed by status, with the detail logged only behind an off-by-default flag because that body can quote the request it rejected. This is gateway-side and takes effect when that service is deployed, not with this BOSS release. The `Content-Length` check was followed by `request.body()`, which buffers everything before the second check runs, so a chunked request with no declared length was unbounded - the body is read through a counting stream now (#136)
- **plugins**: a jar that downloads is vetted before it is loaded, and cleanup is complete. Nothing binds a store row to the plugin id its jar declares - signature enforcement binds the hash to the row and the row to the store's key, not the identity - so an admin uploading the wrong jar is enough, and loading first is too late twice over: `installPlugin` inspects the *incoming* manifest and starts a full api hot swap for a newer api jar, and a jar declaring some other installed plugin would be registered against a path about to be deleted. The manifest is read first and a mismatch refused. The download goes to a `<name>.jar.part` sibling and is moved into place with its signature sidecar, because `downloadPlugin` streams into whatever path it is given and `outputStream()` truncates on open - downloading onto the final name destroys any jar already there the instant the connection opens, and a stream that then dies leaves a truncated file at a name every later launch tries to load. The suffix deliberately does not end in `.jar` so a part file left by a kill is ignored by the directory scan (#156)
- **plugins**: "installed" means usable, in one definition both halves share. The reporter filtered on the raw manager keys while the installer's guard required an entry whose jar exists, and that disagreement re-created the exact silence this feature removes: a binary-incompatible load leaves a `DISABLED` entry while the installer deletes the jar it rejected, so the reporter saw the plugin as present and every *later* dependent of it reported nothing at all. One `installedAndOnDisk` predicate is passed to both now - `state == LOADED || (the jar exists && not recorded incompatible)`. All three clauses were load-bearing: entry-only made Retry report success with nothing installed, jar-only made a *running* plugin whose file had moved look absent (neither the jar reconciler nor the updater repoints the in-memory path), and without the incompatibility clause a registration-time failure - which force-unloads the plugin, returns success and leaves the jar on disk - counted as installed (#156)
- **plugins**: the first-run wizard reported its batch once rather than per iteration. A first-run selection of `[jupyter-notebook, ai-gateway]` - the pick this feature exists for - otherwise prompted for the gateway while the loop was two iterations from installing it, and taking Install raced the wizard's own download: the two paths write different filenames for one plugin id, so neither the path nor the coalescing key collides, two jars land, and the loser fails. Reporting after the loop fixes it and is smaller, since the installed set already contains everything the batch installed. It also covers the wizard's GitHub branch, which reported nowhere at all (#156)
- **plugins**: a declined prompt is remembered for the session, keyed by kind. "Not now" on an *optional* dependency is one answer about that plugin - three consumers declare the gateway optional, and being asked three times for one answer is what this prevents - while "Skip" on a *required* one is keyed by `(dependent, missing)`, because another plugin's hard requirement is a different question and silencing it would be worse. Neither persists: an answer that outlived the session would leave no way to be asked again short of editing a file (#156)

## Improvements

- **plugins**: installs are detached and coalesced process-wide per plugin id. The prompt is driven from a window's scope, so closing that window mid-download would otherwise abort the install and leave a partial jar; and coalescing was per-installer, meaning per window, so the case it most needed to cover - two windows prompting for the same plugin and two concurrent downloads writing one path - was the case it missed (#156)
- **plugins**: the dialog shows the plugin id alongside the store's display name. This is a consent dialog for downloading and running code, and the display name is the one string the least trustworthy party controls. Both attacker-influenced names are clamped with `maxLines`, and a store-supplied version no longer goes unsanitised into a filename, where a version of `../x` wrote outside the plugins directory (#156)
- **plugins**: a success toast confirms the install, since the dependent is deliberately not reloaded. It has already resolved its handle to the dependency, typically to null - survivable because the consumers resolve the API lazily per call, which their own guidance requires anyway since load order is not guaranteed. The toast says the dependent can use it and to relaunch if a feature still reports it missing (#156)
- **plugins**: a system component that is genuinely missing is logged before it is filtered. The microkernel runtime and the api plugin are never offered - one is refused outright by the loader and skipped on scan, the other's install is an unload-all / swap / reload-all hot swap - but filtering them before anything logged produced no prompt *and* no trace, the same silence this feature removes, in the case where a support log matters most (#156)
- **menus**: menus carrying an icon or an inline trailing button still take the drawn path, deliberately. Silently dropping those would remove an affordance rather than restyle it - the sidebar, workspace and run-history menus use them for inline edit and delete. Reshaping them into submenus is the next stage, at which point the eligibility check becomes dead and can go (#157)
- **llm**: `parseGatewayError` delegates to one parser rather than keeping a second that could disagree about what a gateway error looks like, and its test now asserts the property - that the raw body never leaks - rather than an exact sentence (#136, #155)
- **tests**: 66 tests over the dependency feature (1804 in the module) with each round's new rules mutation-checked, 44 over the native menu engine, 28 gateway tests up from 16, 8 filesystem-free cases pinning reload resolution, and `HeavyweightCornerSizingTest` / `ToastOverlayTest` / `NoRawDialogConventionTest` for the overlay work (#136, #150, #151, #156, #157)
